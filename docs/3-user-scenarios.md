## 1. 개요 & 등장인물

본 문서는 Team CalTalk의 핵심 가치인 **"일정과 대화의 맥락 통합 보존"**이 실제 팀 협업 흐름에서 어떻게 작동하는지를 구체적인 서사로 풀어낸 사용자 시나리오 모음이다. 추상적인 요구사항(FR/BR/AC)을 실제 화면 동작·클릭·시스템 메시지·도메인 이벤트와 연결하여, 누가·언제·왜·어떻게 행동하는지를 생생한 예시 데이터로 보여준다. 각 시나리오는 도메인 정의서의 유스케이스(UC-01~UC-06) 및 수용 기준(AC-01~AC-08)과 추적 가능하도록 매핑되며, 설계 검증과 QA 시나리오의 기반으로 사용된다.

### 가상 팀 상황 설정

5인 스타트업 개발팀 **"Rocket팀"**은 신규 결제 기능 출시를 위한 2주 스프린트를 진행 중이다(2026년 6월 1일~6월 12일). 팀은 흩어진 개인 캘린더·메신저·엑셀로 일정을 관리하다 충돌과 누락을 겪은 끝에, 일정과 채팅을 한 화면에서 통합 관리하기 위해 Team CalTalk를 도입했다. 모든 일시는 내부적으로 **UTC로 저장**되며 화면에는 한국 표준시(**KST, UTC+9**)로 표시된다.

### 등장인물

| 인물 | 도메인 역할 | 소속 | 성향/맥락 | 비고 |
|---|---|---|---|---|
| **민지** | 팀장 (Team Leader) | Rocket팀 | 팀 일정의 단일 통제자. 충돌을 빠르게 인지하고 변경 근거를 추적하려 함 | Schedule 등록/수정/삭제, ScheduleChangeRequest 처리 권한 보유 |
| **준호** | 팀원 (Team Member) | Rocket팀 | 백엔드 개발자. 일정 변경이 필요하면 사유를 명확히 전달하려 함 | Schedule 열람 + 채팅 기반 변경 요청 |
| **수아** | 팀원 (Team Member) | Rocket팀 | 프론트엔드 개발자. 조연. 일정 확인과 채팅 참여 | 열람 + 채팅 |
| **태현** | 팀원 (Team Member) | Rocket팀 | QA 담당. 조연. 일정 충돌·테스트 일정에 민감 | 열람 + 채팅 |

> 역할 유일성(BR-10): Rocket팀 내에서 각 사용자는 하나의 역할만 가진다. 민지는 팀장, 나머지는 팀원이다.

## 2. 대표 시나리오 (Happy Path)

> 표기 규칙: 일정은 **Schedule**, 변경 요청은 **ScheduleChangeRequest**, 채팅 메시지는 **ChatMessage**, 일자별 채팅 이력은 **Daily Chat Log**, 알림은 **Notification**으로 통일한다. 시간은 화면 표시 기준 KST이며, 괄호로 UTC를 병기할 수 있다.

### SC-01 회원가입·로그인 후 팀 진입

- **관련 UC/FR/BR**: UC-01 / FR-01, FR-02 / BR-01, BR-02
- **선행 조건**: 준호는 Team CalTalk 계정이 없으며, Rocket팀은 이미 민지에 의해 생성되어 있다.
- **트리거**: 준호가 민지로부터 팀 합류 안내를 받고 서비스에 접속한다.

**단계별 흐름**

1. 준호가 브라우저로 Team CalTalk **로그인/회원가입 화면**에 접속한다. 아직 인증되지 않은 상태이므로 캘린더·채팅 등 어떤 기능에도 접근할 수 없다(BR-01).
2. 준호가 "회원가입" 탭을 클릭하고 이메일 `junho@rocket.io`, 표시이름 "준호", 비밀번호를 입력한 뒤 [가입] 버튼을 누른다.
3. 시스템이 입력값을 검증하고, 비밀번호를 **bcrypt 해시로 저장**(평문 미저장)한 후 User 계정을 생성한다. 가입 완료 후 자동 로그인되어 **JWT 액세스 토큰**이 발급된다.
4. 준호가 Rocket팀에 가입한다(가입 방식은 오픈 이슈 OI-1, 본 시나리오에서는 초대 코드 입력으로 가정). 시스템이 준호의 **Membership(역할: 팀원)**을 생성한다(FR-02, BR-10).
5. 시스템이 준호의 토큰과 Rocket팀 Membership을 검증(BR-01, BR-02)한 뒤 **팀 캘린더 + 채팅 통합 화면**으로 진입시킨다.
6. 화면 좌측/중앙에는 6월 월 뷰 캘린더가, 우측에는 오늘(2026-06-02) 날짜의 Daily Chat Log 패널이 표시된다. 준호는 Rocket팀의 Schedule을 열람할 수 있으나(BR-02), 일정 추가/수정 버튼은 노출되지 않는다(팀원 권한, BR-03).

**기대 결과**: 준호는 인증된 Rocket팀 팀원으로서 통합 화면에 진입했다. 비멤버였다면 진입이 거부되었을 것이다(BR-02). 준호의 역할은 팀원으로 고정되어, 이후 모든 권한 판정의 기준이 된다.

### SC-02 팀장이 스프린트 일정 등록

- **관련 UC/FR/BR**: UC-02 / FR-04 / BR-03, BR-06
- **선행 조건**: 민지는 Rocket팀 팀장으로 로그인되어 통합 화면에 진입해 있다. 해당 시간대에 겹치는 Schedule이 없다.
- **트리거**: 스프린트 중간 점검을 위한 회의 일정을 캘린더에 등록하려 한다.

**단계별 흐름**

1. 민지가 캘린더 월 뷰에서 **2026년 6월 5일(금)** 날짜 칸을 클릭한다.
2. **일정 등록/수정 모달**이 열린다. 민지가 다음을 입력한다.
   - 제목: `스프린트 중간 점검 회의`
   - 시작: `2026-06-05 14:00` (KST) → 내부 저장 `2026-06-05 05:00 UTC`
   - 종료: `2026-06-05 15:00` (KST) → 내부 저장 `2026-06-05 06:00 UTC`
   - 종일 여부: 체크 안 함
3. 민지가 [저장] 버튼을 누른다.
4. 시스템이 **유효성 검사(BR-06)**를 수행한다. `startAt < endAt`(14:00 < 15:00)이 성립하므로 통과한다.
5. 시스템이 **충돌 검사(BR-07)**를 수행한다. 같은 팀의 6/5 시간대에 겹치는 Schedule이 없으므로 충돌이 감지되지 않는다.
6. Schedule이 저장되고 **`ScheduleCreated` 이벤트**가 발생한다. 모달이 닫히고 6월 5일 칸에 `스프린트 중간 점검 회의 14:00~15:00`이 표시된다.
7. 실시간 채널(WebSocket)을 통해 준호·수아·태현의 캘린더에도 동일 일정이 1초 이내에 반영된다(NFR-03).

**기대 결과**: 새 Schedule이 충돌 경고 없이 저장되었으며, 모든 팀원의 화면에 즉시 공유되었다. 일정의 작성자(팀장 민지)와 시간 정보가 단일 출처로 보존된다.

### SC-03 팀장이 일정 등록 시 충돌 경고 발생

- **관련 UC/FR/BR/AC**: UC-02 / FR-06 / BR-07, BR-08 / AC-01, AC-02
- **선행 조건**: SC-02의 결과로 `스프린트 중간 점검 회의 14:00~15:00`(KST) Schedule이 6/5에 존재한다.
- **트리거**: 민지가 같은 날 디자인 리뷰 회의를 추가하려다, 시간대가 겹치는 일정을 등록한다.

**단계별 흐름**

1. 민지가 6월 5일에 새 Schedule을 추가하려고 모달을 연다. 다음을 입력한다.
   - 제목: `디자인 리뷰`
   - 시작: `2026-06-05 14:30` (KST)
   - 종료: `2026-06-05 15:30` (KST)
2. 민지가 [저장]을 누른다.
3. 시스템이 유효성 검사(BR-06)를 통과시킨 뒤 충돌 검사(BR-07)를 수행한다.
   - 기존 A = `14:00~15:00`, 신규 B = `14:30~15:30`
   - 판정식: `A.startAt(14:00) < B.endAt(15:30)` **AND** `B.startAt(14:30) < A.endAt(15:00)` → 둘 다 참 → **충돌**(AC-01).
4. **BR-08에 따라 Schedule은 저장된다(차단하지 않음).** 동시에 **`ScheduleCreated`에 이어 `ScheduleConflictDetected` 이벤트**가 발생한다.
5. 민지 화면에 충돌 경고 **Notification**이 표시된다.
   > ⚠️ "디자인 리뷰(14:30~15:30)가 스프린트 중간 점검 회의(14:00~15:00)와 시간이 겹칩니다. 일정은 저장되었습니다. 시간을 조정하시겠어요?"
6. 민지는 경고를 확인하고 디자인 리뷰를 **15:00~16:00**으로 수정하기로 한다. 모달에서 종료/시작을 조정해 `15:00~16:00`으로 저장한다.
7. 재검사 시: 기존 A = `14:00~15:00`, 수정된 B = `15:00~16:00` → `A.endAt(15:00) == B.startAt(15:00)`. **경계 접촉은 충돌이 아니다**(연산자 `<`, AC-02). 경고 없이 저장된다.

**기대 결과**: 겹침은 즉시 가시화되었으나 일정 저장이 차단되지 않아 팀장이 유연하게 판단·조정할 수 있었다. 경계 접촉(끝=시작) 케이스는 충돌로 오판되지 않았다.

### SC-04 팀원이 캘린더에서 일정 확인 + 일자별 채팅으로 맥락 회수

- **관련 UC/FR/BR**: UC-03, UC-06 / FR-03, FR-07 / BR-05
- **선행 조건**: 6/5에 `스프린트 중간 점검 회의 14:00~15:00`, `디자인 리뷰 15:00~16:00` 두 Schedule이 존재한다. 준호는 팀원으로 로그인되어 있다.
- **트리거**: 준호가 6/5 회의 준비 상황을 파악하려 캘린더와 채팅을 함께 확인한다.

**단계별 흐름**

1. 준호가 캘린더에서 **6월 5일(금)** 날짜를 클릭(선택)한다. 일 뷰로 두 Schedule이 시간순으로 표시된다(FR-03). 준호는 열람만 가능하며 수정 버튼은 없다(BR-03, UC-03).
2. 날짜 선택과 동시에 우측 채팅 패널이 **선택 날짜(targetDate=2026-06-05)의 Daily Chat Log**로 동기화된다(UC-06, BR-05).
3. 준호가 채팅 입력창에 메시지를 작성한다.
   - 작성 시각(createdAt): `2026-06-02 11:20 KST`
   - 본문: "6/5 중간 점검 회의 전에 결제 API 1차 통합 끝내겠습니다. 디자인 리뷰는 그 직후라 이어서 참여 가능해요."
4. 준호가 [전송]을 누른다. 시스템이 ChatMessage를 생성하고, 준호가 보고 있던 날짜를 기준으로 **targetDate=2026-06-05**를 자동 부여한다(도메인 4.1). createdAt(6/2)과 targetDate(6/5)가 다른 점에 유의 — "어느 날짜의 맥락에 대한 메시지인가"는 6/5다.
5. 메시지가 WebSocket으로 수아·태현·민지 화면에 1초 이내 반영된다(NFR-03). 수아가 곧이어 "프론트 결제 화면도 6/5 전까지 1차 붙여둘게요"라고 응답하며 같은 Daily Chat Log에 누적된다.
6. 며칠 뒤(6/4) 태현이 6/5 회의 맥락을 회수하기 위해 캘린더에서 다시 6월 5일을 선택하면, 6/5 두 Schedule과 함께 위 대화들이 그대로 보존되어 표시된다(BR-05).

**기대 결과**: 일정과 그에 관한 대화가 같은 화면·같은 날짜 컨텍스트로 묶여 보존되었다. 시간이 지나도 특정 날짜의 일정과 논의 맥락을 한 번에 회수할 수 있다.

### SC-05 팀원의 채팅 기반 일정 변경 요청 → 팀장이 반영(Applied) — 핵심 차별점

- **관련 UC/FR/BR**: UC-04, UC-05 / FR-08, FR-09 / BR-04, BR-09
- **선행 조건**: 6/5 `스프린트 중간 점검 회의 14:00~15:00` Schedule이 존재한다. 준호는 팀원, 민지는 팀장으로 로그인되어 있다.
- **트리거**: 외부 협력사 미팅이 14시에 잡혀, 준호가 중간 점검 회의 시간을 미뤄달라고 요청한다.

**단계별 흐름**

1. 준호가 캘린더에서 6/5의 `스프린트 중간 점검 회의` Schedule을 연다. 팀원이므로 직접 수정할 수 없다(BR-03). 대신 일정 옆 [변경 요청] 액션을 사용한다(BR-04).
2. 준호가 변경 요청 폼/채팅에 사유와 희망안을 입력한다.
   - 대상 Schedule: `스프린트 중간 점검 회의` (scheduleId 연결)
   - 본문: "협력사 결제 연동 미팅이 6/5 14:00에 확정됐어요. 중간 점검 회의를 **16:00~17:00로 미뤄** 주실 수 있을까요?"
   - 작성 시각: `2026-06-03 09:40 KST`, targetDate=2026-06-05
3. 준호가 [요청 전송]을 누른다. 시스템이 다음을 수행한다.
   - **ChatMessage**를 생성하여 6/5 Daily Chat Log에 기록한다(BR-05). 이 메시지의 messageId가 **originMessageId**가 된다.
   - 해당 ChatMessage를 매개로 **ScheduleChangeRequest**를 생성하고 상태를 **Requested**로 설정한다(BR-04, BR-09). 요청자=준호, 대상 scheduleId 연결, originMessageId 연결.
   - **`ScheduleChangeRequested` 이벤트**가 발생하고, 팀장 민지에게 요청 **Notification**이 전달된다.
4. 민지가 화면 내 알림을 통해 **변경 요청 처리** 화면을 연다. Requested 목록에서 준호의 요청을 선택하면, **원본 채팅(originMessage) 링크**를 통해 6/5 Daily Chat Log의 해당 대화 맥락("협력사 미팅 확정")을 바로 확인할 수 있다.
5. 민지가 사유에 공감하고 수용을 결정한다. 대상 Schedule을 `16:00~17:00`(KST)으로 수정하고 [반영(Applied)] 버튼을 누른다.
6. 시스템이 다음을 수행한다.
   - Schedule을 수정 저장하고 충돌 검사(BR-07)를 재수행한다(16:00~17:00에 겹치는 일정 없음 → 경고 없음).
   - ScheduleChangeRequest 상태를 **Requested → Applied**로 전이한다(BR-09, AC-07). 처리자=민지, 처리시각 기록.
   - **`ScheduleUpdated` + `ScheduleChangeApplied` 이벤트**가 발생한다.
   - 요청자 준호와 팀 전체에 **변경 공유 Notification**이 전달되고, 캘린더의 일정이 모든 팀원 화면에서 `16:00~17:00`으로 갱신된다(NFR-03).
7. 6/5 Daily Chat Log에는 준호의 원 요청 메시지("협력사 미팅 확정 → 16시로")와 반영 결과가 연결되어 그대로 남는다.

**핵심 차별점 강조**: 일정이 14:00→16:00으로 바뀐 **"결과"**뿐 아니라 **"왜 바뀌었는가(협력사 미팅 확정)"**라는 근거가 **Daily Chat Log(채팅 이력)에 originMessageId로 영구 연결**되어 보존된다. 다른 도구는 변경 결과만 남기고 근거를 흘려보내지만, Team CalTalk은 변경 근거를 채팅 맥락에 묶어 언제든 추적 가능하게 한다. 이 연결률은 PRD의 North Star Metric(Applied 변경 중 originMessageId 연결 비율 100%)으로 측정된다.

**기대 결과**: 팀원의 변경 요청이 채팅 근거와 함께 팀장에게 전달되었고, 팀장이 권한 범위 내에서 일정을 수정·반영하여 팀 전체에 공유되었다. 변경의 결과와 근거가 모두 보존되었다.

---

### SC-06 팀장이 변경 요청을 반려(Rejected)

- **관련 UC/FR/BR/AC**: UC-05 / FR-09 / BR-09 / AC-08
- **선행 조건**: 6/8(월) `배포 점검 11:00~12:00` Schedule이 존재한다. 수아가 변경 요청을 생성해 둔 상태다.
- **트리거**: 수아가 배포 점검을 6/9로 미뤄달라고 요청했으나, 출시 일정상 변경이 불가하다.

**단계별 흐름**

1. 수아가 채팅으로 ScheduleChangeRequest를 생성한다(BR-04).
   - 본문: "6/8 배포 점검을 6/9 오전으로 미룰 수 있을까요? 프론트 QA가 하루 더 필요해요."
   - 작성 시각: `2026-06-05 16:10 KST`, targetDate=2026-06-08
   - 상태: **Requested**, originMessageId 연결, `ScheduleChangeRequested` 발생 → 민지에게 Notification.
2. 민지가 변경 요청 처리 화면에서 수아의 요청과 원본 채팅 맥락을 확인한다.
3. 민지는 출시일이 6/10으로 고정되어 배포 점검을 미룰 수 없다고 판단한다. [반려(Rejected)] 버튼을 누르고, 반려 사유(선택 입력, OI-7)를 작성한다.
   > 반려 사유: "출시일(6/10) 고정으로 6/8 배포 점검은 유지해야 합니다. 대신 6/9 오전에 추가 QA 시간을 별도로 잡을게요."
4. 시스템이 ScheduleChangeRequest 상태를 **Requested → Rejected**로 전이한다(BR-09). 처리자=민지, 처리시각 기록. **대상 Schedule은 변경되지 않는다.**
5. **`ScheduleChangeRejected` 이벤트**가 발생하고, 요청자 수아에게 반려 통지 Notification(반려 사유 포함)이 전달된다.
6. 해당 요청은 이제 **종결 상태**다. 이후 누구도 이 요청을 다시 반영/반려로 전이할 수 없다(AC-08). 수아가 재시도가 필요하면 **새 ScheduleChangeRequest**를 생성해야 한다.
7. 6/8 Daily Chat Log에는 수아의 원 요청과 민지의 반려 사유가 맥락으로 보존된다(BR-05).

**기대 결과**: 변경이 수용되지 않았음에도 요청과 반려 사유가 채팅 이력에 근거로 남았다. 종결된 요청은 불변이며, Schedule은 영향받지 않았다.

|---|---|---|---|---|

## 5. 가정 및 참고

본 시나리오는 도메인 정의서 v0.2와 PRD v0.1의 정의를 따르며, 다음 가정과 미결 사항을 전제로 한다(PRD 14장 오픈 이슈 연계).

- **팀 가입 방식 (OI-1)**: SC-01에서 준호의 가입을 "초대 코드 입력"으로 가정했다. 실제 방식(초대 코드 vs 이메일 초대 vs 오픈 가입)은 MVP 단순화 방안으로 결정 예정이며, 결정에 따라 SC-01 2~4단계의 화면 흐름이 조정될 수 있다.
- **최초 팀장 지정 (OI-2)**: 민지가 Rocket팀의 팀장인 것은 "팀 생성자=팀장 자동 부여"를 가정한 것이다. 역할 유일성(BR-10)과 정합하도록 확정이 필요하다.
- **targetDate 부여 UX (OI-3)**: SC-04/SC-05에서 메시지의 targetDate는 "사용자가 보고 있던(선택한) 날짜"를 기준으로 자동 부여된다고 가정했다(도메인 4.1). 선택 날짜 vs createdAt 환산의 화면 표현은 구현 세부로 미결이다.
- **반려 사유 입력 (OI-7)**: SC-06에서 민지가 반려 사유를 입력했다. 도메인상 반려 사유는 선택 항목이며, 필수/선택 여부의 UX 결정은 미결이다.
- **화면 내 Notification 보존 범위 (OI-5)**: 충돌 경고·변경 공유 등 Notification의 세션 한정 vs 영속 보존은 미결이며, Should 항목으로 시간 여유에 따라 결정된다.
- **시간 표기 원칙 (NFR-05)**: 모든 일시는 내부적으로 **UTC로 저장**되고 화면에는 **사용자 시간대(KST)**로 변환 표시된다. 충돌 비교는 분(minute) 단위로 수행된다(BR-07).
