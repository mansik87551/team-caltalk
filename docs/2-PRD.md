## 2. 제품 개요 / 비전

**Team CalTalk**은 4~10명 규모의 IT 개발팀·스타트업이 **팀 일정 관리와 실시간 채팅을 하나의 화면에서 통합**하여, 흩어진 캘린더·메신저·엑셀로 인한 일정 충돌과 맥락 손실을 줄이는 웹 협업 도구다. 팀장이 팀 일정(Schedule)의 단일 권한자로서 일정을 통제하고, 팀원은 일정을 열람하며 변경이 필요할 때 채팅으로 ScheduleChangeRequest를 생성한다. 모든 일정 변경은 채팅 이력에 근거가 남아, 명확한 책임 체계 위에서 일정과 소통이 일원화된다.

### 핵심 가치 제안

| 가치 | 설명 |
|---|---|
| **맥락 보존 (핵심 차별점)** | 일정을 변경할 때 그 근거가 **Daily Chat Log(채팅 이력)**에 남는다. ScheduleChangeRequest는 채팅 메시지(ChatMessage)를 매개로 발생하므로, "왜 이렇게 바뀌었는가"를 항상 추적할 수 있다. |
| 통합 화면 | 캘린더(월/주/일)와 채팅을 한 화면에서 함께 보며 맥락을 즉시 회수한다. |
| 명확한 책임 체계 | 팀장에게 일정 수정 권한을 집중하고(SSOT), 팀원은 채팅 기반 변경 요청으로 참여한다. |
| 일정 충돌 가시화 | 충돌을 감지해 팀장에게 경고하되 저장은 차단하지 않아, 유연성과 가시성을 동시에 확보한다. |

## 3. 배경 & 문제 정의

도메인 정의서 2장의 문제 정의를 PRD 관점에서 요약한다.

| 문제 | 영향 | 해결 방향 |
|---|---|---|
| 일정이 개인 캘린더·메신저·엑셀로 흩어져 있음 | 충돌·중복·누락 발생 | 팀 단위 통합 캘린더(월/주/일)로 일정 단일화 |
| 일정과 대화가 분리되어 맥락 회수가 어려움 | 변경 사유·이력 추적 곤란 | 캘린더+채팅 통합 화면, targetDate 기준 Daily Chat Log 보존 |
| 팀장이 팀 일정을 직접 제어하기 어려움 | 일정 책임 소재 불명확 | 팀장에 수정 권한 집중, 팀원은 채팅 기반 변경 요청(ScheduleChangeRequest) |

기존 협업 도구는 일정 변경의 "결과"만 남기고 "근거"를 흘려보낸다. Team CalTalk은 변경 근거를 채팅 맥락으로 묶어 보존한다는 점에서 차별화된다.

## 4. 목표 & 성공 지표(KPI)

### 비즈니스 목표
- 4~10명 팀이 일정과 소통을 한 곳에서 운영하도록 한다.
- **3,000개 이상의 팀이 동시에 프로젝트를 진행**할 수 있는 동시성·확장성을 확보한다.
- 일정 변경 시 채팅 이력으로 근거를 보존하는 차별점을 정착시킨다.

### North Star Metric
> **활성 팀당 "채팅 근거가 연결된 일정 변경(ScheduleChangeApplied)" 주간 건수** — 통합 일정/채팅 가치가 실제로 사용되고 있음을 가장 잘 대표하는 단일 지표.

### 성공 지표

| 분류 | 지표 | 목표치(MVP) | 측정 방법 |
|---|---|---|---|
| North Star | 팀당 주간 ScheduleChangeApplied 건수 | ≥ 2건/활성팀/주 | 이벤트 로그 집계 |
| 확장성 | 동시 운영 가능 팀 수 | ≥ 3,000팀 | 부하 테스트(추정 부하 기준, NFR-02 참조) |
| 활성화 | 팀 생성 후 7일 내 일정 1건+채팅 1건 등록 비율 | ≥ 60% | 온보딩 퍼널 분석 |
| 핵심 기능 채택 | ScheduleChangeRequest를 사용하는 팀 비율 | ≥ 40% | 기능 사용 로그 |
| 맥락 보존 | Applied 변경 중 originMessageId(채팅 근거)가 연결된 비율 | 100% | 데이터 정합성 검증 |
| 실시간성 | 채팅/일정 반영 체감 지연 P95 | ≤ 1초 | 클라이언트 RTT 측정(NFR-03) |
| 안정성 | 핵심 API 성공률 | ≥ 99% | 서버 로그/모니터링 |

## 5. 목표 사용자 & 페르소나

**목표 사용자**: 4~10명 규모의 IT 개발팀, 스타트업, 소프트웨어 하우스. 웹 브라우저 중심 업무 환경.

| 페르소나 | 역할(도메인) | 핵심 니즈 | 주요 행동 |
|---|---|---|---|
| **민지 (팀장)** | Team Leader | 팀 일정의 단일 통제, 변경 근거 추적 | 일정 등록/수정/삭제, 충돌 경고 확인, 변경 요청 Applied/Rejected 처리 |
| **준호 (팀원)** | Team Member | 일정 열람, 변경 사유 명확히 전달 | 캘린더 조회, 채팅으로 ScheduleChangeRequest 생성, 일자별 맥락 확인 |

> 상세 시나리오는 본 MVP 범위에서 간략화한다.

## 6. 범위(Scope)

도메인 정의서 11장과 정합한다.

### In-Scope (MVP)

| 항목 | 비고 |
|---|---|
| 사용자 인증(FR-01) | 회원가입/로그인, 비밀번호 해시 |
| 팀/멤버십 관리(FR-02) | 팀 생성, 팀장/팀원 역할, 초대/가입 |
| 팀 일정 조회 — 월/주/일 뷰(FR-03) | 권한과 무관히 멤버 조회 가능 |
| 팀 일정 등록(FR-04) | 팀장 한정, 유효성(BR-06)·충돌 검사(BR-07) |
| 팀 일정 수정/삭제(FR-05) | 팀장 한정 |
| 충돌 감지·경고(FR-06) | 저장 유지 + 경고(BR-08) |
| 팀 채팅 및 Daily Chat Log(FR-07) | targetDate 기준 일자별 이력 |
| 일정 변경 요청(FR-08) | 채팅 기반 ScheduleChangeRequest |
| 변경 요청 처리(FR-09) | 팀장이 Applied/Rejected, 결과 공유 |
| 화면 내 Notification | 충돌 경고/변경 공유 등 1차 통지 |
| 반응형 UI | 데스크톱 우선, 모바일 화면 대응 |

### Out-of-Scope

| 항목 | 사유 |
|---|---|
| 외부 연동(Google Calendar, Slack, Outlook 등) | 이번 범위 제외, 추후 적용 |
| 모바일 네이티브 앱 | 웹 우선, 반응형으로만 대응 |
| 접근성(WCAG 등) 대응 | 이번 앱에서 미고려 |
| 모바일 푸시 알림 고도화 | 화면 내 통지로 대체 |
| 개인 전용 캘린더, 다중 팀 통합 뷰 | 도메인 정의서 Out-of-Scope |
| 반복 일정, 결재/승인 워크플로우, 화상회의·파일공유 | 도메인 정의서 Out-of-Scope |

## 7. 기능 요구사항

도메인 정의서 FR-01~FR-09를 PRD 관점으로 확장한다. 우선순위는 **MoSCoW**로 표기하며 **5일 1인 개발 MVP** 기준으로 현실화했다.

| FR | 기능 | 사용자 스토리 | 핵심 동작/규칙 | 우선순위 |
|---|---|---|---|:---:|
| FR-01 | 사용자 인증 | 사용자로서 내 계정으로 안전하게 접근하기 위해 로그인한다. | 회원가입/로그인, 비밀번호 해시, 인증 전제(BR-01) | **Must** |
| FR-02 | 팀/멤버십 관리 | 사용자로서 팀에 속해 일정·채팅을 공유하기 위해 팀을 만들고 가입한다. | 팀 생성, 팀장/팀원 역할, 역할 유일성(BR-10), 팀 소속 전제(BR-02) | **Must** |
| FR-03 | 팀 일정 조회 | 팀원으로서 팀 일정을 파악하기 위해 월/주/일 뷰로 조회한다. | 멤버 조회 가능(BR-02). 월·주·일 뷰 | **Must** (월/일), Should(주 뷰) |
| FR-04 | 팀 일정 등록 | 팀장으로서 팀 일정을 통제하기 위해 Schedule을 추가한다. | 팀장 한정(BR-03), 유효성(BR-06), 충돌 검사(BR-07), `ScheduleCreated` | **Must** |
| FR-05 | 팀 일정 수정/삭제 | 팀장으로서 변경된 상황을 반영하기 위해 Schedule을 수정·삭제한다. | 팀장 한정(BR-03), 자기 자신 제외 충돌 판정(BR-07), `ScheduleUpdated` | **Must** |
| FR-06 | 충돌 감지·경고 | 팀장으로서 일정 겹침을 인지하기 위해 충돌 경고를 받는다. | 판정식·경계 접촉 제외·종일 정규화(BR-07), 저장 유지+경고(BR-08), `ScheduleConflictDetected` | **Must** |
| FR-07 | 팀 채팅 및 Daily Chat Log | 사용자로서 일정 맥락을 공유·회수하기 위해 채팅하고 일자별 이력을 본다. | ChatMessage 작성/조회, targetDate 그룹핑(BR-05), 실시간 전달 | **Must** |
| FR-08 | 일정 변경 요청 | 팀원으로서 일정 변경 근거를 남기기 위해 채팅으로 변경을 요청한다. | 채팅 기반 ScheduleChangeRequest 생성→Requested(BR-04, BR-09), originMessageId 연결, `ScheduleChangeRequested` | **Must** |
| FR-09 | 변경 요청 처리 | 팀장으로서 요청을 결정하기 위해 Applied/Rejected로 처리하고 결과를 공유한다. | 상태 전이표(BR-09), 종결 불변(AC-08), `ScheduleChangeApplied`/`ScheduleChangeRejected` | **Must**(처리), Should(반려 사유) |
| — | 화면 내 Notification | 사용자로서 변화를 놓치지 않기 위해 화면 내 통지를 받는다. | 도메인 이벤트 기반 통지, 충돌/변경 공유 | **Should** |
| — | 팀장 권한 위임/다중 관리자 | — | 도메인 향후 고려사항 | **Could** (Out-of-Scope 후보) |

> MVP 5일 제약상 **주 뷰, 반려 사유 입력, 화면 내 Notification 고도화**는 Should로 두고, 시간이 부족하면 후순위 처리한다.

## 8. 비기능 요구사항(NFR)

| ID | 분류 | 요구사항 | 측정 기준(목표) |
|---|---|---|---|
| NFR-01 | 성능 | 핵심 API(일정 조회/등록, 채팅 송수신) 응답 지연 | P95 ≤ 300ms(서버 처리 기준) |
| NFR-02 | 확장성 | 3,000팀 동시 운영. 팀당 4~10명, 활성 동시 접속 추정 약 1,500~3,000 동접(전체 팀의 5~10% 동시 활성 가정) | 부하 테스트에서 P95 응답 ≤ 1초, 에러율 ≤ 1% 유지. DB 인덱싱(teamId, targetDate, startAt/endAt) 및 커넥션 풀링 적용 |
| NFR-03 | 실시간성 | 채팅 메시지 및 일정 변경의 타 사용자 화면 반영 지연 | 동일 팀 멤버 화면 반영 P95 ≤ 1초 |
| NFR-04 | 보안 | 인증/권한, 비밀번호 보호 | 모든 기능 인증 전제(BR-01)·팀 소속 검증(BR-02). 비밀번호 **bcrypt(또는 argon2) 해시** 저장, 평문 미저장. 권한 매트릭스(도메인 5장) 서버측 강제 |
| NFR-05 | 데이터 정합성 | 시간/날짜 처리 | 모든 일시 **UTC 저장**, 분 단위 충돌 비교(BR-07), 표시 시 사용자 시간대 변환 |
| NFR-06 | 가용성 | 서비스 가동률 | MVP 기준 단일 인스턴스 가용성 목표 99% (운영 SLA는 추후 정의) |
| NFR-07 | 브라우저 지원 | 최신 웹 표준 브라우저 | Chrome/Edge/Firefox/Safari 최신 2개 버전 |
| NFR-08 | 반응형 | 화면 크기 대응 | 데스크톱(≥1024px) 우선, 태블릿/모바일 폭에서 레이아웃 무너짐 없음. 모바일 우선 아님 |
| NFR-09 | 접근성 | (이번 범위 제외) | 미적용. 향후 항목 |

> NFR-02의 동접 추정치는 MVP 부하 테스트의 목표 설정용 가정치이며, 정밀 수치는 실사용 데이터로 보정한다.

## 9. 기술 스택 & 아키텍처 개요

### 기술 스택

> 아래 표는 PRD 분석을 거쳐 **확정된 기술 스택**이다(선정 근거·대안 비교·탈락 사유 상세는 `docs/4-project-structure-principles.md` 4·6장 및 기술 스택 선정 분석 참조). 버전은 stable/LTS 라인 기준이며 정확한 패치 버전은 설치 시점에 고정한다.

| 분류 | 레이어 | 확정 기술 | 비고 |
|---|---|---|---|
| 공통 | 언어 | **TypeScript** (프론트·백엔드 도메인 규칙 모듈 우선) | 프론트엔드(.tsx)와 백엔드 도메인 모듈을 TS로 시작, 백엔드 나머지는 .js 허용. 전면 TS는 향후(구조원칙 7.3) |
| 공통 | 품질 도구 | **ESLint + Prettier** | 린트·포맷 통일. push 시 lint + 단위 테스트를 CI 최소 게이트로 |
| 프론트 | 프레임워크 | **React 18** | SPA, 반응형. 캘린더+채팅 통합 화면 |
| 프론트 | 빌드 도구 | **Vite 5** | 빠른 HMR·zero-config TS, 5일 개발 생산성 |
| 프론트 | 라우팅 | **react-router-dom 6** | 화면 2~3개 규모에 충분, 사실상 표준 |
| 프론트 | 서버 상태 | **TanStack Query v5 (React Query)** | 캐싱·무효화로 일정/채팅 실시간 갱신 반영(NFR-03) |
| 프론트 | 클라이언트 상태 | **Zustand** | 인증·선택 날짜·팀 컨텍스트 등 소수 전역 상태 경량 관리 |
| 프론트 | HTTP | **axios** | 인터셉터로 JWT 주입·에러 표준화 일원화 |

| 프론트 | 캘린더 UI | **FullCalendar (@fullcalendar/react)** | 월/주/일 뷰 즉시 제공(FR-03), 자체 구현 금지 |
| 프론트 | 실시간 | **socket.io-client v4** | 서버 socket.io와 짝, 재연결·룸 위임 |
| 프론트 | 날짜/시간 | **date-fns + date-fns-tz** | UTC↔로컬 변환 단일화(NFR-05), 경량 트리쉐이킹 |

### 구성도 (텍스트)

```
[React SPA (브라우저)]
   │  REST(HTTPS)  ─────────────►  인증/일정/팀/요청 처리
   │  WebSocket    ◄────────────►  채팅 송수신, 일정·요청 변경 실시간 푸시
   ▼
[Node.js + Express API 서버]
   ├─ Auth (JWT 발급/검증, 비밀번호 해시)
   ├─ Domain Service (Schedule, ChatMessage, ScheduleChangeRequest)
   ├─ 충돌 판정 엔진 (BR-07)
   └─ 도메인 이벤트 → 화면 내 Notification 트리거
   ▼
[PostgreSQL]  Users / Teams / Memberships / Schedules / ChatMessages / ScheduleChangeRequests
```

### 실시간 통신 방식 제안: **WebSocket 권장**

| 방식 | 장점 | 단점 | MVP 적합성 |
|---|---|---|---|
| **WebSocket (권장)** | 양방향, 채팅 송신·수신 모두 단일 채널, 낮은 지연 | 연결 관리·스케일링 시 sticky/pub-sub 필요 | 채팅이 핵심이라 양방향성 필수 → **채택** |
| SSE | 서버→클라 단방향, 구현 단순 | 클라→서버는 별도 REST 필요, 채팅 송신에 부적합 | 보조 후보 |

> **근거**: 채팅(FR-07)은 양방향 실시간이 본질이므로 WebSocket이 적합하다. 1인 5일 MVP에서는 `socket.io` 등 검증된 라이브러리로 재연결·룸(팀 단위 채널) 관리 부담을 줄인다. NFR-02 확장 시 Redis pub/sub로 다중 인스턴스 브로드캐스트를 확장한다(MVP에서는 단일 인스턴스 + 룸).

### 인증 방식 제안: **JWT**
- 무상태 토큰으로 수평 확장 시 세션 스토어 부담이 없어 3,000팀 확장 목표(NFR-02)에 유리.
- 모든 REST·WebSocket 핸드셰이크에서 토큰 검증, 팀 소속/역할(BR-02, BR-03)을 서버측에서 강제.

### 프레임워크 선택 근거: **React SPA 채택 (Next.js 대비)**

프론트엔드 프레임워크로 Next.js를 검토했으나, 본 프로젝트 성격상 **React 18 + Vite(SPA)** 를 채택한다. Next.js의 핵심 강점(SSR/SSG/RSC/SEO)이 이 프로젝트에서는 대부분 무효화되고, 제약과는 오히려 마찰을 일으키기 때문이다.

| 평가 축 | React 18 + Vite (SPA, 채택) | Next.js | 이 프로젝트 판정 |
|---|---|---|---|
| SEO / 초기 렌더 | 약함(CSR) | 강함(SSR/SSG) | **무차별** — 인증(BR-01) 뒤 도구라 SEO 불필요 |
| 5일 1인 생산성 | 단순·직관, 셋업 빠름 | App Router/RSC 학습비용 | **React** (P2 단순성) |
| 실시간(socket.io) | SPA와 자연스러움 | 서버리스 배포가 상시 WebSocket 미지원 | **React** (NFR-03) |
| 별도 Express 백엔드 | 역할 분리 명확 | API Routes와 역할 중복·혼선 | **React** |
| 클라이언트 상태 스택 | TanStack Query·Zustand·socket.io-client 자연 정합 | 대부분 `"use client"`로 묶여 RSC 이점 상실 | **React** |
| 자동 성능 최적화 | 수동(코드 스플리팅 등) | 자동(이미지·폰트·프리페치) | Next.js (단 효익 작음) |

**결정적 근거**: ① Team CalTalk은 **로그인 뒤에 있는 팀 내부 도구**라 SEO/SSR 효익이 없다. ② 실시간 채팅·일정 반영(socket.io 상시 연결)은 Next.js 서버리스 모델과 충돌해 결국 별도 WebSocket 서버가 필요하다. ③ 백엔드는 이미 별도 Express(`server/`)로 확정되어 Next.js API Routes와 역할이 중복된다. ④ App Router·RSC의 학습·디버깅 비용은 5일 1인 MVP의 단순성 원칙(P2)에 역행한다.

> 성능 최적화는 Vite 환경의 `React.lazy` 코드 스플리팅 + TanStack Query 캐싱으로 NFR-01(P95 ≤ 300ms) 대응이 가능하다. Next.js 재검토 시점은 공개 랜딩/SEO 페이지 도입 또는 풀스택 단일 코드베이스 통합이 필요해질 때다(향후 확장).

## 10. 사용자 흐름 / 주요 화면

| 화면 | 목적 | 핵심 요소 |
|---|---|---|
| **로그인/회원가입** | 인증 진입(UC-01) | 이메일/비밀번호, 가입, 오류 처리 |
| **팀 캘린더 + 채팅 통합 화면 (핵심)** | 일정과 대화를 한 화면에서 | 좌측/중앙 캘린더(월/주/일 뷰), 우측 채팅 패널(선택 날짜의 Daily Chat Log), 상단 팀 전환·날짜 선택 |
| **일정 등록/수정 모달** | 팀장의 Schedule CRUD(UC-02) | 제목, startAt/endAt, 종일 여부, 유효성·충돌 경고 표시 |
| **변경 요청 처리** | 팀장의 요청 처리(UC-05) | Requested 목록, 원본 채팅(originMessage) 링크, Applied/Rejected 버튼 |

### 핵심 레이아웃 강조
**캘린더와 채팅을 한 화면에서 동시에** 본다. 사용자가 캘린더에서 특정 날짜를 선택하면, 우측 채팅 패널이 해당 날짜의 Daily Chat Log(targetDate 기준)로 동기화되어 일정과 대화 맥락을 함께 회수한다(UC-06).

### 핵심 흐름
1. **로그인 → 팀 진입(UC-01)**: 인증·팀 소속 검증 후 통합 화면 진입.
2. **팀장 일정 등록(UC-02)**: 등록 시 유효성(BR-06)·충돌(BR-07) 검사 → 충돌 시 저장+경고(BR-08).
3. **팀원 변경 요청(UC-04)**: 채팅으로 ScheduleChangeRequest 생성 → Requested, 채팅 이력에 근거 보존.
4. **팀장 요청 처리(UC-05)**: Applied(일정 수정 반영) 또는 Rejected → 결과 팀 공유.
